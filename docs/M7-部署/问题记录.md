## 已确认的容器编排约束

- Compose 项目规范名为 `skilllearningagents`，与当前 PostgreSQL 容器的 `com.docker.compose.project` 标签一致。
- PostgreSQL/PGvector、后端和前端必须由同一份 Compose 项目编排，共用 `skilllearningagents_default` 网络；后续反向代理也纳入该项目。
- 保留现有 `skilllearningagents_pgdata` 数据卷，不通过修改项目名创建一套与现有数据隔离的新卷。
- `docker-compose.yml` 显式声明 `name: skilllearningagents`，避免启动目录变化导致 Compose 项目名漂移。
- 基础 Compose 采用生产安全默认值，不发布 PostgreSQL/后端端口；本地开发通过 dev override 保留 PostgreSQL `localhost:15432`。
- 实施时只进行一次带 dev override 的容器重建并继续挂载 `skilllearningagents_pgdata`；之后用户仍通过 Docker Desktop 启停现有 `techstack-postgres`。
- 提供本地 PostgreSQL 重建/恢复脚本作为备用入口，但不要求用户改变日常 Docker Desktop 工作流。

## 已确认的入口拓扑

- 采用三容器结构：`frontend`、`backend`、`postgres`，全部属于 `skilllearningagents` Compose 项目。
- `frontend` 使用 Caddy 作为 Vue 生产运行时：同一容器服务静态文件、处理 SPA 回退、自动申请/续期 HTTPS，并反向代理后端路径。
- 仅 `frontend` 对外发布 80/443；`backend:18080` 与 `postgres:5432` 仅通过 Compose 默认网络通信，生产环境不直接暴露公网端口。
- Caddy 必须正确转发 `/api`、`/oauth2`、`/login`、`/sse`、`/mcp`，并验证 SSE 不被缓冲、OAuth 回调协议与主机名正确。

## 已确认的镜像发布流程

- 公开 GitHub 仓库使用标准 GitHub Actions Runner 执行后端测试、前端测试和生产构建。
- Docker Buildx 发布 `linux/amd64`、`linux/arm64` 双架构公开镜像：`ghcr.io/into7ou/devguide-backend` 与 `ghcr.io/into7ou/devguide-frontend`。
- Pull Request 只验证、不发布；合入 `main` 或发布版本后才推送镜像，镜像不得包含 `.env`、密钥、Token 或生产数据。
- OCI 初期采用人工确认部署，只执行镜像拉取与 Compose 更新；不把 OCI SSH 私钥或生产环境变量交给 GitHub Actions。

## 已确认的版本发布与回滚

- 首次正式部署版本为 `v0.7.0`，同次发布的前端、后端镜像必须使用相同不可变版本标签，并同时保留 Git Commit SHA 标签用于精确追溯。
- 生产 Compose 通过必填 `IMAGE_TAG` 固定镜像版本，不使用可漂移的 `latest` 或 `main` 作为生产部署依据；`main` 标签仅可用于开发或候选验证。
- 人工发布顺序为：确认并生成部署前数据库备份 → 拉取同版本前后端镜像 → 更新 Compose → 执行健康与关键路径检查 → 记录当前成功版本。
- 应用失败且数据库变更向后兼容时，可把 `IMAGE_TAG` 切回上一成功版本；存在不兼容 Flyway 迁移时不得只回滚应用，必须采用前向修复或经确认恢复部署前备份。
- 实施与演练见 [ISSUE-009](../issues/M7/ISSUE-009-release-rollback.md)。

## 已确认的数据迁移边界

- 当前本地数据库内容基线为：`tech_stacks` 26 条、`vector_store` 44 条、`users` 1 条、`user_tokens` 1 条。
- OCI 首次上线迁移数据库结构、Flyway 历史、`tech_stacks` 与 `vector_store` 内容，以保留动态转正结果和 RAG 展示资料。
- `users` 与 `user_tokens` 表保留结构但不迁移任何数据；生产环境使用全新的 `TOKEN_CIPHER_KEY`，用户在生产站点首次 OAuth 登录时重新建立身份与 Token。
- 脱敏逻辑备份保存在仓库外，不提交 Git、不打入容器镜像；恢复顺序为 PostgreSQL → 脱敏导入 → 后端 Flyway 校验/启动。

## 已确认的生产备份策略

- 首次迁移包与上线后的灾备用途不同：首次迁移继续排除 `users`、`user_tokens`，生产灾备则备份生产全库，确保可以恢复上线后产生的账号与业务数据。
- 生产 PostgreSQL 每日执行压缩逻辑备份；备份在离开 OCI 实例前使用非对称公钥加密，只在服务器保存加密公钥，解密私钥由用户离线保管。
- 密文上传到私有 OCI Object Storage Bucket，保留 7 个日备份和 4 个周备份；明文临时文件必须在上传成功或失败清理流程中移除。
- Bucket 不公开、不进入 GitHub Actions；访问权限遵循最小权限。对象存储服务端静态加密是额外保护，不能替代上传前加密。
- 上线验收至少完成一次“下载密文 → 离线解密 → 临时数据库恢复 → 数据抽样”的恢复演练；仅看到定时任务成功不算备份可用。
- 实施与验收跟踪见 [ISSUE-006](../issues/M7/ISSUE-006-production-backup.md)。

## 已确认的上线目标

- M7 首次上线用于简历与面试展示，为面试官提供可公开访问的 DevGuide 网站，不以商业流量或高并发为目标。
- 优先级依次为：稳定可访问、HTTPS 与基本安全、低固定成本、部署和故障恢复简单。
- 首发不要求中国大陆节点或 ICP 备案，可选择香港、新加坡、日本等境外区域；后续有真实用户和大陆访问要求时再评估迁移。
- 单实例 Compose 部署应保持云厂商可迁移性，不依赖特定 PaaS 的专有数据库或编排能力。

## 暂定托管路线

- 首先尝试申请 OCI Always Free 境外实例，优先选择对目标访问者网络相对合适且有容量的亚洲区域。
- 只有在 OCI 注册、容量或稳定性无法满足时，才重新比较其他低成本平台；目前不预先锁定 Hetzner、AWS 或其他付费兜底。
- Compose、数据卷备份和部署说明必须保持云厂商无关，以便 OCI 不可用时迁移到普通 Linux VPS。

- DevGuide 的规范公开地址确定为 `devguide.into7ou.is-a.dev`；`into7ou.is-a.dev` 保留给未来个人主页。申请阶段可让两个地址暂时指向同一部署，但 OAuth、文档和简历统一使用 DevGuide 规范地址。
- 该地址必须支持公网 HTTPS 与 GitHub OAuth 生产回调，验收以 DNS 生效、证书签发和真实浏览器登录为准。
- `is-a.dev` 是社区维护的免费子域名，不视为用户拥有的独立域名，也不假设存在商业 SLA。
- `FRONTEND_BASE_URL`、OAuth 回调和反向代理站点名保持环境变量化或部署配置化，未来迁移到自有域名时无需修改业务代码。

## 已确认的 OAuth 环境隔离

- GitHub OAuth App 不复用开发与生产 Callback：现有开发 App 继续服务 `localhost:18080`，不修改本地 Client ID/Secret。
- 单独创建 `DevGuide Production` OAuth App，Homepage 为 `https://devguide.into7ou.is-a.dev`，Callback 精确设置为 `https://devguide.into7ou.is-a.dev/login/oauth2/code/github`。
- 生产 OAuth App 关闭 Callback 通配符匹配且不启用 Device Flow；生产 Client Secret 只写入 OCI 受保护的运行时 `.env`。
- 该外部配置由用户在 GitHub 完成，跟踪见 [ISSUE-005](../issues/M7/ISSUE-005-production-domain-oauth.md)。

## 已确认的访问模型

- 采用“公开展示、登录后生成”：匿名面试官可浏览已有技术栈、已有详情与已保存学习资料。
- 动态技术栈发现、实时 Agent 问答、联网搜索和资料回写必须完成 GitHub OAuth 登录，防止匿名请求消耗模型额度或污染资料库。
- 后续必须增加自有注册/登录、强化认证与抗滥用能力，但不作为当前 M7 首次上线的阻断项；见 [认证与抗滥用问题](../issues/auth/ISSUE-001-registration-auth-abuse-protection.md)。
- DDoS 防护不等同于登录认证：后续需同时考虑边缘限流/WAF、登录尝试限制、生成配额、Bot Challenge 和审计告警。
- 匿名前端使用 `/api/v1/showcase/tech-stacks` 只读接口；详情只接受数据库已收录名称，可返回缓存的 GitHub Top10，未知名称返回 404。
- 现有 `/api/v1/tech-stacks` 动态发现链路继续要求登录，避免匿名构造名称触发模型、Tavily 或数据库写入。

## 已确认的生成成本熔断

- M7 在生产环境加入最低限度的服务端生成准入：每个 GitHub 用户每 UTC 日最多 10 次 Agent 请求、20 次动态搜索，全站最多并发执行 2 个生成任务；开发环境默认不启用限制。
- 超限请求返回 HTTP 429、稳定错误码和可用的重试提示，且必须在调用模型、Tavily、GitHub 或资料回写之前拒绝。
- 当前计数和并发状态使用单实例内存实现，与 M7 单后端实例边界一致；并发许可必须在成功、异常和 SSE 取消时释放。
- 业务入口只依赖可替换的生成准入接口，配额规则与状态存储分离。未来用户量增长时可迁移到 Redis/分布式限流和任务队列，并结合共享 Session 横向扩容，本阶段不实现。
- 该机制只保护生成成本，不替代边缘 DDoS 防护和后续注册/登录安全增强；实施见 [ISSUE-007](../issues/M7/ISSUE-007-generation-admission-control.md)。

## 已确认的可用性监控

- 采用零成本双层监控：UptimeRobot 从 OCI 外部每 5 分钟检查规范站点首页和 `/api/health`，OCI Monitoring 监控实例 CPU、磁盘与实例状态。
- 外部监控应验证 HTTPS 响应和健康响应中的 `UP` 关键字，覆盖 DNS、证书、Caddy、反向代理与后端进程不可用；不得调用模型或其他计费接口。
- OCI 告警通过 Notifications 发送邮件，用于定位主机资源或实例异常；告警邮箱、UptimeRobot 账户和 OCI 通知订阅不写入仓库。
- M7 验收需要人为执行一次无破坏的告警演练，证明故障与恢复通知均可到达；实施见 [ISSUE-008](../issues/M7/ISSUE-008-availability-monitoring.md)。

## 已确认的生产日志策略

- 生产日志只用于短期排障，不属于需要长期保留或随数据库灾备恢复的业务数据；日志不进入 PostgreSQL 备份、对象存储备份或 Docker 命名卷。
- 每个服务的应用日志最多保留 7 天且总量最多 50 MB，任一条件先达到即清理旧日志；Docker 自身诊断日志同时配置受支持的大小轮转，禁止直接删除正在写入的日志文件。
- 生产默认 `INFO`，关闭 SQL、Spring Security 等调试输出；不得记录完整用户提问、搜索词、原始资料/JSON、Token、Cookie、OAuth 信息、API Key 或数据库连接密钥。
- 只保留随机请求 ID、接口模板、状态码、耗时、错误类型及必要的非敏感业务标识；Caddy 访问日志去除查询参数和认证/会话 Header，健康探测日志可降噪。
- 当前不引入集中日志平台；未来多实例时可将同一字段与脱敏边界迁移到 OpenTelemetry/Loki 等方案。实施见 [ISSUE-010](../issues/M7/ISSUE-010-production-logging.md)。
