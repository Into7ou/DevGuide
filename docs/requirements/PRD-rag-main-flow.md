# RAG 主流程增强：本地检索优先与可核对的引用

所属阶段：M6.5 后续增强
创建日期：2026-09-03
更新日期：2026-09-03
状态：代码已实现，自动化回归通过，真实接口联调已验证本地检索、联网补充和回写

关联：[总需求 F4](../需求确认书与开发计划.md)、[业务术语](../../CONTEXT.md)

## 用户目标

将检索纳入页面学习问答的主流程。以“Java 里的 Controller 是什么概念”为例，先检索本地 PGvector；本地资料不足以回答时，Agent 联网获取相关内容，并提供精确来源链接和对应原文，帮助用户获得有依据的完整回答。

## 已确认方向

1. 页面发起的学习问答必须先执行本地知识库检索。
2. 本地资料优先用于回答；资料不足时再联网补充。
3. 回答需要具体文档出处，包括原文链接和对应原文内容。
4. 延续用户约束：采用简单实现，不做过度设计或防御性设计。
5. 由现有 Agent 判断本地资料能否覆盖问题关键点；存在明确缺口时，围绕缺口联网补充。
6. 允许跨技术栈检索，但必须向用户澄清资料涉及哪些技术栈及其适用边界。
7. 通常在回答开头标明涉及的技术栈及适用范围；存在会明显改变答案的关键歧义时，先向用户追问。
8. 允许自动回写联网资料，但必须由 Agent 选择有参考价值的原文片段；保留来源链接及所属技术栈，不将模型总结作为来源原文保存。
9. 通过价值筛选、每次问答最多新增 3 个片段及重复内容复用，控制入库数据的无效增长；性能验收标准待定。
10. 资料来源采用官方优先、第三方补充；第三方资料须经 Agent 评估质量、来源明确、能够取得原文，并向用户明确标注其身份。
11. 联网后证据仍不足时，允许提供有引用支持的部分回答，明确指出未确认的问题及缺少的资料。
12. 支持基于上一轮内容继续追问。每次追问独立获得联网补充预算；明确要求更多资料时，应重新联网扩展，避免只重复上一答。

## 实施前的差距（历史基线）

- 页面 `LearnPanel` 使用 `/api/v1/agent/multi/stream`，由 ResearchAgent 自主选择工具，目前不保证先检索本地资料。
- `searchKnowledge` 按语义相似度返回片段，没有独立的“这些资料是否足以回答当前问题”的明确判断流程。
- 原 `/api/v1/agent/learn` 具备资料准备、向量检索和生成链路，但当前页面没有调用该固定链路。
- 当前页面展示流式回答，没有对应的检索结果及原文依据展示。
- 当前联网工具返回标题、截断摘要和链接；页面问答链路尚未将联网获得的正文写回本地知识库。
- 当前 `LearnRequest` 只有技术栈名与本次问题，页面每次生成前清空上一答，尚未传递追问所需的会话上下文。

## 已确认：联网触发标准

由现有 Agent 根据用户问题与检索片段判断是否能覆盖问题关键点；有明确缺口时，围绕缺口联网补充。语义相似度用于寻找相关资料，不单独作为“足以回答”的证明。

示例：用户问“Controller 与 Service 有什么区别”，本地资料只说明 Controller 的职责，尚不足以完成对比，需补充缺失资料。

2026-09-03 用户已接受此标准，现由 ResearchAgent 执行资料覆盖判断。

## 已确认：本地检索范围与技术边界

当前 `searchKnowledge` 支持可选技术栈过滤；传入技术栈时按资料元数据中的名称精确匹配。

允许结合问题跨技术栈进行本地语义检索，将当前页面的技术栈作为理解问题的上下文。例如在 Java 页面询问 Controller 时，可以检索相关 Spring MVC / Spring Boot 资料。

用户明确要求：必须澄清检索内容可能涉及哪些技术栈，确保边界。回答应说明所用资料的技术适用范围，避免将框架特有用法表述为整个语言的通用规则。

## 已确认：如何向用户澄清技术边界

在回答开头说明涉及的技术栈与适用范围；仅当问题存在会明显改变答案的多种解读时，先向用户追问。2026-09-03 用户已接受此交互方式。

示例说明：“以下以 Spring MVC 的 Controller 为例，注解和配置说明适用于 Spring MVC。”

## 已确认：联网资料回写与增长约束

自动回写本次成功取得原文、来源明确且实际用于回答的资料片段，同时保留来源链接及所属技术栈，供后续问答检索复用。回写对象是来源原文，不能把模型生成的回答或总结标作来源原文。

用户补充条件：必须由 Agent 只选择有参考价值的资料片段入库，防止数据过多影响后续访问速度。因此，“本次用过”本身不足以决定入库，还需筛选其后续复用价值。

这是增长与性能目标，尚未测得当前系统存在由数据量导致的性能故障。当前配置已有 HNSW 向量索引；具体查询性能仍需在实施时验证，不能仅凭 Agent 筛选就保证。

## 已确认：首版资料入库规则

2026-09-03 用户已接受以下规则：

- Agent 优先选择能补齐本地知识缺口、可独立理解且可用于后续类似问题的原文片段，例如概念定义、关键机制、典型用法与限制说明。
- 每次问答最多新增 3 个经过筛选的资料片段，无合适片段时不新增；该上限不限制本次回答可参考的资料数量。
- 已有的重复片段复用，不重复新增。

每次新增上限与去重用于控制无效增长，不等于长期总容量上限或查询延迟保证；来源规则见下文，实测性能与限制见阶段验收。

## 已确认：资料来源优先级

优先使用对应技术的官方文档、标准组织资料和官方项目 README；这些资料不足时，允许补充由 Agent 评估质量、来源明确且能取得原文的第三方技术资料，并向用户明确标注第三方身份。

回答及候选入库资料均遵循这一优先级；第三方资料入库仍须满足已确认的实际引用、原文获取、复用价值、数量上限及去重要求。2026-09-03 用户已接受此来源策略。

## 已确认：联网后仍有证据缺口时的回答

回答已获得依据的部分，明确列出尚未确认的关键点，并说明缺少什么资料；没有足够依据时不将模型猜测补写为确定结论。

“完整且全面”的验收边界为：尽量覆盖当前问题，但不承诺每次检索都能找到全部答案。2026-09-03 用户已接受这种部分回答方式。

## 最后三个技术决策

用户已结束答案输出方面的讨论，仅保留三个技术问题，逐项确认后立即开始代码编辑。实施中的普通细节采用符合已确认需求的简单方案，不继续扩展问答轮次。

### 第 1/3 项：资料回写时序（已确认）

先完成回答，再使用现有后台执行机制进行向量化与回写，让本次回答不等待入库完成。回写失败不撤回已完成的回答，记录失败结果；不新增消息队列或持久化任务系统。

取舍：回答结束后可能有短暂的入库延迟，紧接着的提问不保证能立即检索到新增片段。2026-09-03 用户已接受此异步回写方式。

### 第 2/3 项：联网补充预算与追问（已确认）

设置可配置上限，首版默认每次问答最多执行 2 轮联网补充；每轮最多 1 次搜索、抓取 3 个页面正文。Agent 在本次问题所需资料足够时提前结束补充，第二轮后仍不足则按已确认规则提供有依据的部分回答。

该预算用于控制联网调用成本和等待时间，不要求每次用满轮次，也不改变每次最多新增 3 个入库片段的约束。2026-09-03 用户接受此执行预算，并补充以下追问要求：

- 预算按每次提问独立计算，不是整段对话共享两轮预算。
- 用户问过 Controller 概念后，可以继续问“还有更多关于 Controller 的内容吗”。系统应理解延续的主题和已回答内容，再次获得最多两轮联网补充机会，每轮仍为一次搜索、最多三个页面正文。
- 追问仍先检索本地资料；明确要求更多内容属于新增资料需求，应发起新的联网补充，不能仅以上一答已充分为由跳过扩展。本轮已获得所需补充后可以提前结束。

### 第 3/3 项：追问上下文保存范围（已确认）

由当前页面内存保留最近 3 轮已完成问答及引用信息作为发送给后端的上下文，用来理解“还有更多吗”等省略主题的问题及已讨论内容。历史回答用于理解语境，新的回答依据仍通过检索取得。

刷新页面或切换技术栈页面时清空这段临时会话；首版不建立数据库会话历史表。该方案能支持连续追问，但不提供跨刷新或跨设备恢复。

用户已确认并授权开始代码编辑。页面保留当前会话中所有已输出的轮次，支持折叠前轮回答并明确显示轮次分界；“最近 3 轮”只限制发送给后端的上下文，不表示删除页面上更早的回答。
