# M5 用户体系 — 技术要点（面试可讲）

> 所属阶段：M5 用户体系
> 更新日期：2026-09-04
> 状态：用户体系功能已完成；生产安全基线已补齐，首次部署采用单实例会话

> 每个点用「是什么 → 作用 → 为什么」三句话讲清，点到为止。

## 1. GitHub OAuth2 登录（授权码模式）
- **是什么**：让用户用 GitHub 账号登录，而不是自己注册。
- **作用**：程序员用户直接 GitHub 登录，顺带拿到用户身份。
- **为什么**：目标用户是程序员，GitHub 账号几乎人人都有，省去注册。

## 2. OAuth2 授权码流程
- **是什么**：登录时跳 GitHub → 用户授权 → GitHub 回调 → 后端拿授权码换 token。
- **作用**：完成「登录 → 拿到用户信息 + access token」的闭环。
- **为什么**：授权码模式最安全（token 不经过前端，走后端换取）。

## 3. Token 加密存储
- **是什么**：用户的 GitHub access token 用带 `v2:` 版本标识的 `Encryptors.stronger` 加密后存数据库；至少 32 字符的密钥由环境变量提供。
- **作用**：避免明文 token 落库，并可在轮换期使用历史密钥读取旧数据；旧版无前缀密文仍可兼容解密。
- **为什么**：token 明文泄漏等于账号泄漏；版本化密文和轮换窗口还能避免升级算法或更换密钥时一次性破坏已有数据。

## 4. 用户各自绑定 Token
- **是什么**：登录后 GitHub API 调用改用「当前用户自己的 token」。
- **作用**：每个用户独立的 GitHub 限流额度（5000 次/小时）。
- **为什么**：多人共享一个应用 token 会撞限流；各自绑定后互不影响。

## 5. 技术栈作用一览
| 技术 | 作用 |
|---|---|
| Spring Security | 认证/鉴权框架 |
| OAuth2 Client | GitHub 授权码登录 |
| users / user_tokens 表 | 用户 + Token 持久化 |
| 对称加密（AES-PBKDF2） | Token 加密存储 |
| Session Cookie | 登录态保持 |
| /api/auth/me | 前端查询当前登录用户 |

## 6. Token 生命周期兜底（过期/撤销降级）
- **是什么**：用户绑定 token 过期或失效（GitHub 返回 401）时，自动清掉这条 token，回退用应用级 token 重试一次。
- **作用**：避免用户撤销授权后，GitHub 相关功能「永久报错」，用户不用重新登录也能继续用。
- **为什么**：绑定的 token 是不可控的外部凭据（用户随时能撤销），必须有「失效降级」兜底，否则一个失效 token 会卡死整个功能。

## 7. 单行 Token 模型（upsert）
- **是什么**：每个用户只保留一条 token 记录，靠 `user_id` 唯一约束 + `ON CONFLICT DO UPDATE` 原子覆盖。
- **作用**：登录时覆盖旧 token，不产生无限膨胀的历史行；并发登录也不会插入重复记录。
- **为什么**：当前业务只消费「最新一条 token」，历史行是纯垃圾数据；单行模型更简单、查询更快、语义更清晰。

## 8. 安全默认值（fail-fast 密钥）
- **是什么**：加密密钥 `TOKEN_CIPHER_KEY` 不设默认值，少于 32 字符、未配置或仍为占位值时启动直接失败。
- **作用**：防止生产环境漏配密钥，导致全库 token 用公开常量可解密。
- **为什么**：安全配置要「显式且拒绝降级」，静默用弱默认值等于把「漏配」变成「数据泄露」。

## 9. API 鉴权与 CSRF
- **是什么**：健康检查、当前登录态和 OAuth 入口保持公开，其余 API/MCP 默认要求登录；浏览器写请求还必须携带服务端签发的 CSRF Token。
- **作用**：匿名用户无法直接调用业务能力，已登录用户也不能被第三方页面借用 Cookie 发起写操作。
- **为什么**：Session Cookie 会被浏览器自动携带，认证和 CSRF 必须同时处理，不能只做其中一层。

## 10. 单实例会话边界
- **是什么**：首次 M7 部署只运行一个后端实例，Session 和 OAuth Authorized Client 暂由进程内机制管理。
- **作用**：在不提前引入共享状态基础设施的情况下保证登录链路行为确定。
- **为什么**：多实例会要求共享 Session 和授权信息；在流量尚未需要横向扩展时，明确单实例约束比制造一个表面可扩容、实际会随机掉登录态的部署更可靠。
