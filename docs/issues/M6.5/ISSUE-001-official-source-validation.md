## 现象、复现与影响

首页搜索未收录的 C语言。GitHub 搜索返回 `binary-husky/gpt_academic`，其 homepage 为
`https://github.com/binary-husky/gpt_academic/wiki/online`。旧逻辑把该地址展示为官方文档并永久入库。
真实数据库复现：`id=24` 的 C语言 保存了此地址。预期应指向 C 语言维护/标准组织的官方资料。

## 已确认根因

1. 直接选取星数排序结果中第一个格式合法的 homepage，没有检查仓库与技术的身份关系。
2. Tavily 无域名匹配时仍退回任意首个合法 URL；格式合法不代表官方归属正确。
3. 已入库记录不再走发现流程，单改新记录准入无法修复旧链接。

固定数据探针证实：只交换仓库顺序，输出官网即随之改变；命中已有记录不会调用发现服务。

## 修复

- 删除 homepage 直接转正和 Tavily 任意结果兜底。先识别技术实体及官方归属，再检索实际资料。
- 候选需匹配识别出的官方站点及项目路径；共享域名如 GitHub 还必须限定 owner/repo。
- 用资料标题、摘要核验同一实体和发布者归属；模型只返回候选下标，入库 URL 取自实际搜索结果。
- 无法核验时返回 503，不写库；官方仓库自己的 Wiki 仍可通过归属核验，不做全站封禁。
- 人工核验 C 短名称，统一 `C`、`C语言` 等别名；官方入口为 [WG14 C 工作组](https://www.open-std.org/jtc1/sc22/wg14/)，GitHub 查询改为 `language:C`。
- V7 迁移只匹配已确认的 C语言 + 错误 URL，保留主键并修正链接、别名、关键页和查询词。修复前确认该技术没有向量片段，无需删除向量数据。

## 验收

回归用例先在旧代码复现错误，再在修复后通过。真实接口中 C语言/C 均返回 WG14 链接和 10 个仓库，清单仍保留 `id=24`；Astro 首查成功收录，再查小写名称无重复。
详细结果见 [测试与验收](../../M6.5-动态转正与界面优化/测试与验收.md)。
